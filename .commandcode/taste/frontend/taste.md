# Frontend (Next.js) API-integration preferences

- Reuse the existing API client, data-fetching hooks, and UI primitives; do not create multiple API clients or parallel hook implementations. Explicitly: "Reuse the existing frontend architecture" and "DO NOT create duplicate APIs if an appropriate backend API already exists." Confidence: 0.95
- Use the existing environment variable for the API base URL; never hard-code localhost. Confidence: 0.9
- Use the actual backend routes already implemented; never guess route names or invent endpoints. Confidence: 0.9
- Do not render fake/static numbers once APIs exist; a `null` block from the backend means "not shown to you", never zero, and untracked modules get a notice rather than invented figures. When the backend starts providing a count (e.g., a `members` field on the stats endpoint), wire the previously hardcoded stat card (e.g., "5000+ Members") to the live value, keeping the seeded figure only as fallback. Confidence: 0.9
- Frontend permission checks are for UX only; the backend authorization remains the real security boundary — never assume hiding a button provides security. Confidence: 0.9
- Use backend pagination; never fetch thousands of records and paginate/sort in the browser (no list endpoint accepts sort params — drop interactive column sort on paginated tables). Confidence: 0.85
- Every API-driven page needs loading, empty, and error states — no blank screens; reuse existing skeleton/spinner/empty/error components; loading behavior must not cause layout problems (no layout shift). Confidence: 0.85
- After a successful mutation: show success feedback, revalidate/refresh the affected data, close the modal, reset the form — no full page reload. Confidence: 0.85
- Never use floating-point math for financial logic; handle Decimal strings with string-only helpers and display money safely. Confidence: 0.9
- Avoid `any` unless absolutely unavoidable; keep frontend types consistent with backend DTOs (money as string). Prefer type-safe alternatives to `as any` even for awkward library types — e.g., annotate `gsap.utils.toArray()` results as `gsap.TweenTarget[]` rather than casting the whole array. Confidence: 0.9
- Never put secrets in NEXT_PUBLIC_* variables; never expose passwords, tokens, or hashes client-side. Confidence: 0.9
- Debounce search inputs; don't fetch data for modules/pages the user lacks permission to see. Confidence: 0.8
- Optional content sections (events, services, announcements, funds) must be conditionally rendered: hide the entire section when the API returns zero rows or fails — never show empty cards, placeholder records, or fake content; "do not invent database records" and "remove mock data only where a real backend API exists." Confidence: 0.95
- Isolate failures per section: one failed API must never break the rest of the page — each section fetches independently so the others keep working (e.g., prayer times still render when the events API fails). "One failed API must NOT break the entire homepage." Confidence: 0.95
- Public pages must consume only public-safe, unauthenticated endpoints; never use admin/authenticated endpoints for public data. If a public endpoint exposes sensitive fields (private donor/user info, internal transaction data, audit logs, admin-only fields), stop and report it — never mask sensitive fields only in React. Confidence: 0.95
- Preserve the existing UI/visual design both when integrating data and when adding new sections/content: reuse the existing containers, typography, cards, icons, buttons, spacing, and responsive patterns; do not redesign the existing page or introduce an unrelated design system ("DO NOT redesign the existing Home Page", "Do not introduce an unrelated design system"). Confidence: 0.95
- Only advertise functionality that actually exists in the application — inspect the repository/routes before listing capabilities or linking to features, and never advertise unavailable ones ("Only advertise functionality that actually exists... Do not advertise unavailable features"). Confidence: 0.9
- Writes content for beginner/low-experience users (rural audiences) in very simple language, and requires small-screen comfort down to 320px: no horizontal scrolling, readable text, tap targets large enough to tap (~44px+), no overflowing cards or overlapping sections — responsive checks requested across a fixed set of widths (320/350/375/390/412/768/1024/1440). Confidence: 0.75
