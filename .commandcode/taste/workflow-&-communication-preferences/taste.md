# Workflow & communication preferences
- Delivers large work as numbered "parts" and wants each part implemented, verified, and reported before the next ("Implement PART 1 ONLY", "STOP after Part X"). Do not carry on past the stated boundary. Confidence: 0.95
- Treats explicit "Do NOT implement X / Do NOT modify frontend / Do NOT create new APIs" lists as hard scope constraints, not suggestions. Confidence: 0.95
- Wants minimal-change implementation: "Make the minimum required changes" and "Do not modify unrelated features" — keep edits scoped to the task and leave unrelated code (e.g., pre-existing lint debt or unrelated failing tests) untouched. Confidence: 0.9
- Wants the project's verification commands run after every part (prisma validate, prisma generate, build/typecheck, lint, tests) — verification is part of delivery, not optional. Also expects runtime verification: start the app, confirm the page loads, and check browser console + network requests. Confidence: 0.9
- Do not claim something passed unless it was actually tested — explicitly report what could not be verified (e.g., no browser tool available means the in-browser console/network check stays "not confirmed"). Confidence: 0.9
- If a public endpoint exposes sensitive fields (donor/user data, transactions, admin fields), STOP and report the exposure instead of hiding those fields only in the frontend. Confidence: 0.9
- Wants final responses as a structured numbered report following the exact section list the user provides (e.g. "1. Files changed, 2. Prisma changes, 3. Routes, 4. Permissions, 5. Tests, 6. Build/lint/test result, 7. Any blocking issue"; PART 2 specified: files changed, APIs connected, sections connected, sections intentionally static, optional sections conditionally rendered, security issues found/fixed, tests executed, build result, remaining issues). Confidence: 0.9
- Wants only "essential" test cases covering the listed scenarios, not exhaustive suites. Confidence: 0.85
- For public/security-sensitive features, expects a role + tenant test matrix: logged-out user, logged-in normal user, admin, and (if supported) multiple mosque contexts, plus explicit data-exists/data-missing cases for each optional section (funds present → shows; none → hidden; historical rows unchanged after a new one is added; page refresh stays consistent with backend values). Confidence: 0.7
- Values efficiency over over-deliberation ("do not read extra think. follow the instarction"); ask when genuinely blocked, otherwise decide and disclose the decision in the report. Confidence: 0.7
- When an endpoint is missing or a contract mismatches, STOP and report the exact mismatch rather than inventing a new API or behavior. Confidence: 0.9
- Follows instructions literally and wants zero autonomous behavior: explicitly told the agent "not do extra think", "follow only my instruction", and "not do any think without my interaction". Do not take initiative, run extra steps, or proceed without an explicit go-ahead. Confidence: 0.9
- Writes terse, informal follow-ups ("try again", "run the derver", "what is the error", "your response is not good") — respond by acknowledging the failure and re-attempting/fixing the last task rather than requiring clarification. A "try again" after a verification report means actually fix the flagged issues in the changed files so the checks pass clean (e.g., clear the lint errors in the touched component), not merely re-run or re-report them. Confidence: 0.8
- Never guess or infer from a repository — explicitly mark anything not confirmable as "Not confirmed from repository." so the report distinguishes evidence from assumption. Confidence: 0.95
- Runs a dedicated inspect/audit phase before any implementation ("Your first task is ONLY to inspect", "DO NOT MODIFY CODE IN PART 1"), including security/tenant-isolation and performance audits of existing code, and expects the resulting report before any code change. The inspection must be comprehensive: all relevant components, API services/hooks, Tailwind config, CSS variables, animation utilities, image assets, and existing responsive patterns — to identify reusable components, duplicated sections, and root causes of visual problems before editing. Confidence: 0.9
- When an API contract changes (e.g., "add one more field members" to an endpoint), propagate it through the whole stack in one pass — backend DTO, service logic, service spec/tests (with the new field mocked and asserted), frontend service types, and the consuming component — then verify build, tests, typecheck, lint, and the live endpoint response before cleanup. Confidence: 0.8
- Often wants deliverables saved as files in the repo rather than only pasted in chat — e.g. "make a list in the public folder" — so produce the requested Markdown artifact (e.g. in `public/`) in addition to summarizing it. Confidence: 0.6
- Prefers static content over unnecessary backend work: informational sections that need no dynamic data should be static — do not create backend APIs or database records for text that does not need to be dynamic. Confidence: 0.85
